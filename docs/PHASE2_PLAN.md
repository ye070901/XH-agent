### 2.3 基础流水线（全文统一）

```
用户输入（工业机器人调试相关问题）
  → InputGate（闸门1：输入校验 / 敏感过滤 / 意图识别）
    → Agent1 学情诊断（识别用户技能水平、薄弱环节）
      → DiagnosisGate（闸门2：诊断结果合理性检查 / 置信度阈值）
        → Agent2 生成检索 Query
          → RAG 检索（工业机器人知识库）
            → RecallGate（闸门3：召回质量把关，裁决路径 PASS / RETRY / FALLBACK）
              → Agent2 基于知识库生成回答
                → Agent3 初审（逐项核验操作准确性）
                  → Agent4 保真修正（事实核查 + 厂商手册引用校准）
                    → Agent3 再审 → 标准化输出（操作步骤 + 安全提示 + 引用来源）
```

> **注**：流水线中 Agent4 保真修正模块为远期规划，Phase 2 暂不开发。Phase 2 当前重心为搭建基础可用知识库，保障 RAG 链路正常运行。

### 2.4 三闸门裁决路径定义

| 闸门 | 位置 | PASS | RETRY | FALLBACK |
|------|------|------|-------|----------|
| InputGate | 用户输入后 | 校验通过，进入 Agent1 | N/A（前端拦截） | 返回输入引导提示 |
| DiagnosisGate | Agent1 输出后 | 诊断结果合理，进入 Query 生成 | 补充诊断信息后重试（最多 2 次） | 降级为基础诊断模板 |
| RecallGate | RAG 检索后 | 召回满足阈值，进入生成 | 改写 Query 重检（最多 3 次） | 无知识库模式 / 提示无法回答 |

> 三闸门覆盖输入、诊断、召回三个关键节点。末端「标准化输出」步骤自带格式校验与合规检查，不再独立成闸门。

### 2.5 Arch-L — 核心链路 开发工作手册

| 项目 | 内容 |
|------|------|
| **你的定位** | 你负责把整个流水线从输入到输出串起来。所有模块**不依赖知识库**——初期用写死的假数据（mock）跑通逻辑，Day 8 KB 样本到了再换成真检索。 |
| **你需要会什么** | Python 后端开发（FastAPI / Flask 均可），理解状态机/流水线模式。如果你会 asyncio 最好，不会也没关系——同步代码先跑通再改异步。 |
| **代码放哪** | `src/gates/`（三闸门）、`src/scheduler/`（调度）。每个模块单文件不超过 500 行，超过就拆。 |

**Day 1（08-03）：协议设计 + 仓库初始化**

| 做什么 | 怎么做 | 交付标准 |
|--------|--------|----------|
| Gate 接口协议设计 | 写一份 Markdown 文档 `docs/Gate_Protocol.md`，定义 3 个 Gate 的**输入结构、输出结构、裁决枚举**（PASS/RETRY/FALLBACK）。不需要写代码，画清楚接口就行。参考 2.4 的裁决路径表。 | 文档里三个 Gate 的输入/输出 JSON Schema 写清楚，Opt-3 能直接按照这个来对接 EventBus 消息格式 |

**Day 2（08-04）：InputGate v0.1**

| 做什么 | 怎么做 | 交付标准 |
|--------|--------|----------|
| `input_gate.py` | 实现 3 个检查方法：① `_validate_input()` — 非空字符串、长度 ≥ 2；② `_filter_sensitive()` — 关键词黑名单（先写 5 个测试词，后续扩充）；③ `_detect_intent()` — 正则匹配"怎么/如何/为什么/故障/报错/编程/示教/安全"等疑问词，返回意图标签。三个检查串联，全部 PASS → GateResult.PASS，敏感词命中 → FALLBACK。 | 单元测试 `tests/test_input_gate.py`：3 个正常用例、2 个敏感词用例、2 个空输入用例，全部通过 |
| Mock 数据 | 写一个 `tests/mock_responses.py`，里面放 3 条假诊断结果（JSON 格式，模拟 Agent1 的输出——包含"用户水平：初级/中级"、"薄弱环节：坐标系概念/示教器操作"）。给 Opt-3 共用。 | Opt-3 的 EventBus 测试能直接 import 用 |

**Day 3（08-05）：DiagnosisGate v0.1**

| 做什么 | 怎么做 | 交付标准 |
|--------|--------|----------|
| `diagnosis_gate.py` | 检查 Agent1 返回的诊断 JSON：① 置信度字段是否 ≥ 阈值（先写 0.6）；② 诊断结果是否含必填字段（用户水平 + 薄弱环节）；③ 如果置信度不够 → RETRY（带上补充信息提示）；④ 如果格式完全不对 → FALLBACK（降级为"默认初级用户"诊断）。 | 单元测试 5 个用例覆盖 PASS/RETRY/FALLBACK 三条路径 |
| 与 Day 2 联调 | 手写一条流水线脚本：InputGate check → Agent1 mock → DiagnosisGate check，三个环节串起来跑通 | 终端打印 "流水线 Day 3 联调通过" |

**Day 4（08-06）：RecallGate v0.1（三闸门收尾）**

| 做什么 | 怎么做 | 交付标准 |
|--------|--------|----------|
| `recall_gate.py` | 检查 RAG 检索返回结果：① 召回文档数量 ≥ 1 → PASS；② 召回数为 0 → 改写 Query（从原始 Query 中提取核心名词，组成新 Query 字符串），标记 RETRY 并返回新 Query；③ 重试 3 次仍为 0 → FALLBACK，返回"知识库暂无相关数据"。 | 单元测试 6 个用例：3 个 PASS（1篇/3篇/10篇）、2 个 RETRY（0篇→改写）、1 个 FALLBACK（3次后0篇） |

### 2.6 API 接口硬性约束

> **硬性约束**：所有迭代优化过程中，API 接口严格保持与原有接口定义完全吻合，不修改入参、出参结构，杜绝前后端接口不适配问题。

| 约束项 | 说明 |
|--------|------|
| 入参结构不可变 | `POST /api/generate` 请求体格式固定为 `{"user_input": str}`，后续迭代不得增删改字段 |
| 出参结构不可变 | 响应体顶层结构固定，后续迭代仅在已有字段内部扩展内容，不修改字段名和类型 |
| 路由不可变 | API 路由路径、HTTP 方法保持稳定，不新增/删除/变更路由 |
| 变更流程 | 如需调整接口，须经全员评审并同步更新 `docs/api.md`，确保前后端一致 |

### 3.2 采集自检流程与合格标准

> **核心原则**：每日采集量小（1~2 篇/人），每篇采集完成后必须立刻自检。自检通过方可提交至 `data/raw/`；不通过则修正后重新自检，仍不通过则放弃该篇、不计入当日配额。

#### 3.2.1 自检流程

```
采集完成
  ↓
逐项自检（按 3.2.2 合格判定表逐项打勾）
  ↓
┌─ 全部通过 ──→ 提交至 data/raw/Kx_xxx/，计入当日配额
│
└─ 有不通过项
      ↓
   判断是否可修正
      ↓
   ┌─ 可修正项 ──→ 当场修正 → 修正后重新逐项自检（最多 2 轮）
   │
   └─ 硬性红线（一票否决）──→ 放弃该篇，不计入当日配额
```

#### 3.2.2 合格判定标准

> 以下 **7 项检查全部通过**方判定为合格。任一硬性红线不通过即一票否决。

| 编号 | 检查项 | 类型 | 合格标准 | 不合格处理 |
|------|--------|------|----------|-----------|
| ① | **主题合规** | 🔴 硬性红线 | 内容属于工业机器人编程与调试领域，且不属于 3.4 禁止采集清单中任何一类 | **一票否决**：删除该篇或移至 `docs/reference/`，不计入配额 |
| ② | **权威等级** | 🔴 硬性红线 | 标注了 A 或 B 等级（C 级不合格） | **一票否决**：找 A/B 级对应来源替换为合格文档；找不到则放弃 |
| ③ | **来源可追溯** | 🔴 硬性红线 | 含可访问的 URL 链接，且链接可正常打开 | **一票否决**：补充来源 URL；无法补充则放弃 |

  chunk_size / overlap / 切分边界 参数调整
