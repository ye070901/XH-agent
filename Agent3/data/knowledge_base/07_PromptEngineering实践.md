# Prompt Engineering 最佳实践

## 什么是 Prompt Engineering

Prompt Engineering 是设计和优化 LLM 输入提示词的系统性方法。一个好的 prompt 能够显著提升 LLM 输出的质量、准确性和一致性。在多 Agent 系统中，每个 Agent 的 prompt 设计直接影响整个系统的可靠性。

## 基本原则

### 1. 明确角色设定
为 LLM 指定一个清晰的角色，帮助模型进入正确的"思维模式"。

```
你是严格的内容审核专家。检查学习资源质量，但不要修改内容。
```

### 2. 结构化输出要求
明确指定期望的输出格式，推荐使用 JSON schema：

```
输出必须为严格的 JSON 格式：
{
    "verdict": "approved|needs_revision",
    "issues": [{"severity": "error|warning|info", "detail": "..."}]
}
```

### 3. 提供具体规则
用明确的规则替代模糊的要求：

```
不好: "检查内容是否准确"
好的: "检查: API名称是否正确? 概念定义是否有误? 代码示例能否运行?"
```

### 4. 分步骤引导
将复杂任务分解为明确的步骤：

```
1. 提取所有事实断言
2. 源原文比对
3. 判定 accurate/hallucination/unverifiable
4. 生成审核报告
```

## 高级策略

### Few-Shot Prompting
在 prompt 中提供 1-3 个示例，帮助模型理解期望的输出格式和推理方式。

### Chain-of-Thought（思维链）
引导模型逐步推理而非直接给出答案：
```
请逐步分析: 首先检查API名称，然后验证概念定义，最后评估代码正确性。
```

### 对比提示（Constitutional AI）
在 prompt 中同时给出"好的示例"和"不好的示例"：
```
好的审核: 指出具体错误 + 给出修正建议 + 引用知识库原文
不好的审核: 只说"内容有问题"
```

## 各 Agent 的温度设置

| Agent 类型 | 推荐温度 | 原因 |
|-----------|---------|------|
| 诊断 Agent | 0.1-0.2 | 需要一致、稳定的判断 |
| 生成 Agent | 0.3-0.5 | 需要一定的创造性和多样性 |
| 审核 Agent | 0.1 | 需要严格一致的事实判断 |

## 常见问题

### 幻觉产生的原因
- prompt 过于开放，没有约束检索范围
- 缺少"不知道就说不知道"的指引
- 上下文超过模型的有效窗口

### 输出格式不稳定的解决方案
- 在 system prompt 中重复格式要求
- 使用 `response_format: json_object` 强制 JSON 输出
- 在代码层做 JSON 容错解析

## 中文 Prompt 设计注意事项

1. 使用中文指令时，保持句式简短清晰
2. 中英文混用时，关键术语保持英文（如 API 名称）
3. markdown 格式在中文环境下同样有效
